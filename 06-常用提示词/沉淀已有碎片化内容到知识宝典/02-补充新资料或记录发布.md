# 第2个提示词：补充新资料或记录发布

请在已有模块知识的基础上，处理本次新增材料或正式发布信息，并把变化回写到知识宝典中。

本阶段不另起一份平行的模块文档，不重新整理全系统，不编造新增材料中没有出现的内容。目标是让知识宝典保持可查、可继续迭代，而不是把所有资料机械搬进去。

两步链路如下：

```text
01 首次整理：把碎片材料整理成模块知识第一版
02 增量维护：有新资料或正式发布时回写已有知识
```

## 一、输入

```text
系统名称：<系统名>
任务模式：<补充新资料 / 整理版本发布 / 两者同时>
目标模块：<模块名>
现有模块知识：<文件路径或内容>
本次新增材料：<文件路径、链接或内容>
可选版本信息：<版本号 / 发布日期 / 发布说明，可空>
知识宝典目录：<知识宝典目录>
```

先读现有模块知识，再处理新增材料。如果现有模块知识缺失，先说明缺口，并建议回到第1个提示词做首次整理；不要在本阶段直接重写全量第一版。

任务模式说明：

- `补充新资料`：把新字段、流程、状态、接口、特殊规则或待确认问题补回现有模块知识；
- `整理版本发布`：在回写模块变化的同时，补一条版本发布日志；没有版本号、日期或发布内容时不要猜测。

两种模式可以同时发生：材料既更新了模块知识，又对应一次正式发布时，先回写模块知识，再记发布日志。

继续沿用第1个提示词的证据状态和有效性：只有材料明确标注、正式发布或人工确认的内容，才能进入模块知识的「当前有效」口径；观察、推断和未解决冲突保留为「候选」或「待确认」，历史材料标为「历史参考」。

## 二、维护边界

1. 以现有模块知识为入口，把已确认或正式发布的变化写回原文，不新建「模块知识-新版」「模块知识-补充」这类平行文档。
2. 原始新增材料仍然保留；知识宝典只沉淀当前工作需要的结构化结论。
3. 新旧说法不一致时，保留差异，并标为`待确认`或`历史参考`，不要静默覆盖旧内容。
4. 新增材料没有提到的章节，保持原样，不要为了“更新感”重写无关部分。
5. 没有材料支撑的版本号、发布日期、影响范围和业务规则，一律不补写。
6. 正式发布内容才写入版本发布日志；临时讨论、未确认方案只进入模块知识的待确认或历史参考，不记成已发布。
7. 输出用途是让人和AI下次能更快找到当前口径，而不是存档所有聊天过程。

## 三、处理步骤

### 1. 对照现有知识

先定位新增材料影响的章节：模块定位、流程状态、页面字段、接口关系、特殊规则或待确认清单。

### 2. 回写模块知识

实际写入前，先根据现有知识和新增材料列出拟变更清单，包括原内容、拟改内容、变更依据、证据状态、有效性和影响章节；未确认的冲突不得覆盖当前口径。

按以下规则更新现有模块知识文件：

- 新字段、状态、操作、接口关系：补入对应表格或章节；
- 已有条目被新材料明确修正且确认属于当前口径：更新正文，并在备注或更新摘要中说明变化依据；
- 新旧冲突且无法判断对错：保留两种说法，标`待确认`或`历史参考`；
- 新材料只提出问题、未给出结论：写入待确认清单，不写成已确认规则。

### 3. 处理版本发布

仅在任务模式包含`整理版本发布`，或新增材料明确对应已正式发布版本时执行：

- 记录版本号、发布日期、发布内容和影响模块；
- 页面没有提供、材料没有写明的信息写「未提供」，不要猜；
- 把对本模块有影响的变化，同步反映到模块知识中。

### 4. 输出更新摘要

最后单独给出本次更新摘要，说明新增了什么、修改了什么、仍待确认什么，方便课堂演示和后续复查。

## 四、输出

### 1. 回写后的模块知识

更新：

```text
<知识宝典目录>/01-核心业务模块/<模块名>.md
```

如果已有知识宝典目录结构，优先沿用已有结构；保持第1个提示词的主体结构，不因增量维护改成另一套目录。若原文件缺少「待确认清单」或「资料来源」等必要章节，可以按需补齐，但不要整体重排成新模板。

### 2. 版本发布日志

仅在需要记录正式发布时，追加或更新。如果已有版本日志路径，优先沿用；以下为默认路径：

```text
<知识宝典目录>/05-版本发布与上线清单/版本发布日志.md
```

使用以下条目结构：

```markdown
## <版本号或未提供版本号>

- 发布日期：
- 影响模块：
- 发布内容：
- 对本模块的影响：
- 资料来源：
- 仍待确认：
```

如果发布日志文件尚不存在，可以创建该文件并写入首条记录；不要因此创建一整套无关目录。

### 3. 本次更新摘要

如果确实发生了内容变化，再输出一份简短摘要；没有实际变化时，只在回复中说明，无需创建空的更新摘要文件：

```text
<知识宝典目录>/01-核心业务模块/<模块名>-更新摘要-<日期或版本>.md
```

结构如下：

```markdown
# <模块名>更新摘要

## 本次任务
- 系统名称：
- 任务模式：
- 目标模块：
- 新增材料：
- 版本信息：

## 新增内容
| 内容 | 写入位置 | 证据状态 | 有效性 | 来源锚点 |
|---|---|---|---|---|

## 修改内容
| 原内容 | 现内容 | 处理方式 | 证据状态 | 有效性 | 来源锚点 |
|---|---|---|---|---|---|

## 仍待确认
| 问题 | 原因 | 建议下一步 |
|---|---|---|

## 文件变更
- 已更新的模块知识：
- 已更新的版本发布日志：有 / 无
```

## 五、交付前检查

1. 是否回写了现有模块知识，而没有另起平行文档？
2. 是否先读了现有知识，再处理新增材料？
3. 新旧冲突是否保留差异并标注，而不是静默覆盖？
4. 未提到的旧章节是否保持原样？
5. 版本发布日志是否只记录正式发布信息，且没有猜测版本号或日期？
6. 更新摘要是否清楚写了新增、修改和仍待确认？
7. 是否没有把未确认方案写成已发布规则？
8. 是否在回写前列出了拟变更清单，并保留了具体来源锚点？

本阶段完成后，知识宝典应仍然只有一份可继续使用的模块知识入口。下次再有碎片材料时，重复本提示词即可，不必每次从零整理。
