# SYZC 单据状态与流转设计规范

> **定位**：定义 SYZC 存货监管系统全平台通用的状态流转原则、动作触发规范、合规防线与不可变性约束。  
> **适用范围**：SYZC 系统所有单据、事件、审批流与主数据设计。

---

## 一、核心设计目标

1. **状态闭环**：单据生命周期必须有始有终，终态必须不可逆，不存在状态死循环。
2. **动作与状态强绑定**：状态不可脱离动作独立存在；每个状态必须有明确的准入动作、准出动作和前置校验。
3. **法律与合规存证**：质押、解押、提货、开锁凭证下发与告警核销必须全路径审计留痕，状态不可篡改。
4. **物联实时性与高可用**：高频物联告警与开锁审批采用专道流转，保障毫秒级至秒级响应。

---

## 二、六大通用设计原则

### 2.1 状态三问原则
每个状态的定义必须清晰回答：
- **现在处于什么监管/业务阶段？**（如：在押质押中、待补仓、开锁待审批）
- **允许执行什么动作？**（如：允许发起解押申请、允许补充质押物）
- **严禁执行什么动作？**（如：严禁提货、严禁出库移库、严禁直接物理删除）

### 2.2 状态变更严禁在表单内直接修改（全局强约束）
- **反例（严禁）**：在详情或编辑页放置一个 `[状态: 在押 ▼]` 的下拉框，用户手动选择改成 `[已解押]` 并点击保存。
- **正例（标准）**：状态字段必须为纯展示只读标签（Badge）。状态变更**必须**通过独立的操作按钮（如【申请解押】、【审核通过】、【解除预警】）触发业务流，弹窗确认并校验前置规则后由系统底层原子性更新。

### 2.3 基础主数据与档案一律禁止物理删除
- **适用对象**：仓库、库区、货位、货主企业、监管企业、设备主档、仓储合同。
- **原因**：历史质押单、存货流水、司法存证和审计日志必须具备长期可追溯性，物理删除会导致历史关联断裂与数据孤立。
- **统一方案**：
  - 仅支持通过**【停用】**或**【作废】**进行状态流转。
  - 停用前必须进行**强校验拦截**：若该对象存在生效中的质押单、在库质押存货或未结案告警，系统强行阻断停用并弹窗提示依赖项。
  - 停用后，新建业务单据时不可再选择该对象，但历史存量单据可正常展示其快照信息。

### 2.4 专网专道实时审批与自审禁止（P06 / R11）
- **专网专道流转**：如【门禁开锁审核】挂载于专道，不接入通用低效工作流引擎，不进通用待处理大池子，专道保障高频开锁实时响应。
- **自审禁止**：审批人严禁审批自己发起的申请。审批列表行及详情中，本人发起的申请仅提供【详情】入口，**严禁提供【去审批】或【去处理】操作入口**；后端 API 必须具备前置拦截校验。

### 2.5 规则版本递增与存量流水不回写（C08 原则）
- **适用对象**：设备预警配置、订单预警配置、开锁审批配置。
- **规则生效边界**：规则编辑保存后内部 Version 递增，最新配置仅对保存后新产生的事件或回调生效；**绝不回写、不更新**既有未处理的历史告警流水或已完结单据。
- **快照不可变**：单据或告警触发时，必须将当时生效的规则内容、阈值快照持久化固化，确保司法追溯证据效力。

### 2.6 并发防重与操作幂等性
- 在涉及质押锁定、解押提货、额度释放、密码凭证生成等核心敏感操作时，必须具备分布式防重锁机制。
- 二次确认弹窗必须带有防重复提交（Disable + Loading）控制，后端必须具备基于唯一业务流水号的幂等校验。
