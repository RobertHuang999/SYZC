## 一、修订原则（草案）

1. **以线上设备上报枚举为上限**：附录 A 子类型必须能 1:1 承接三方推送事件，不允许 PRD 有、设备无。
2. **风险类与事务类分层，但统一入口**：6.2 已合流 `设备预警配置` + `设备事务通知配置`；本草案在**同一附录 A** 内用「子类型分组 + 默认处置策略」区分，不再拆两个配置菜单。
3. **保留 6.2 核心约束**：R01 瞬态防抖=0、R14 上线类单独成规则、R04 设备+子类型唯一、R06 正常事务默认 `已结案 · 有效`。
4. **命名以线上枚举为准**：子类型名称必须与三方实际上报名一致；**禁止**使用 PRD 臆造名（如「被剪」「撬锁」「低电量」「门未关超时」「门禁离线」「正常开关锁事务」等）。
5. **处置策略与状态展示词表（2026-09-08 定稿）**：配置侧 `disposition_mode`——`触发即结案` / `人工解除结案` / `恢复自动结案`；信息侧 `warning_status` 展示——`待处置 · 有效` / `已结案 · 有效` / `已作废`（枚举 OPEN_* / CLOSED_* 不变）。三档均写入设备预警信息。

## 三、与「设备移除」的处理（草案建议）

| 项目 | 6.1 | 6.2 现行 | 本草案建议 |
| :--- | :--- | :--- | :--- |
| 设备移除 | 设备事务通知配置 · 可配规则 | 附录 A **无**子类型；IoT 移除流程承担联动 | **维持 6.2 不设子类型** |

理由：

- 移除是平台侧领域事件，非三方硬件持续上报类型；6.2 迁移文档 §4.4 已明确运行时不再生成「设备移除通知」流水。
- 若业务仍要求「移除成功推短信」，建议在 **IoT 移除设备 PRD** 增加可选通知开关，**不进入附录 A**，避免与 R04 设备+子类型唯一冲突。

历史「设备移除」通知规则迁移：继续写入 `migration_exception` + `legacy_sub_type` 展示，不伪造新子类型。

## 六、对现有 6.2 规则的影响（摘要）

| 规则 | 本草案影响 |
| :--- | :--- |
| **R01** | 安防破坏、事务类、上线类均为瞬态 → 防抖=0 置灰 |
| **R02** | 门未关、设备离线、电量低于20% 为持续 → 防抖 >0 |
| **R04** | 子类型变多，同一设备可配置多条规则（不同子类型） |
| **R06** | 开锁/关锁/上线（可选）走 `已结案 · 有效`；风险类走未处理 |
| **R14** | 挂锁/人脸各自的 `设备上线` 仍须单独成规则 |
| **R13** | 勾选「仅针对新设备」时仍隐藏升级区；仅上线类展示该开关 |
| **订单穿透** | 仅风险类 + 等级 `sync_to_order_warn=true` 时穿透；事务类默认不穿透 |
