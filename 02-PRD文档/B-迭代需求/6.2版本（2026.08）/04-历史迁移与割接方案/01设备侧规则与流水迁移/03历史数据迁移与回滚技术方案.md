# 03/02 设备预警配置历史数据迁移与回滚技术方案

> **文档定位**：指导 6.1 设备预警配置、事务通知配置和设备事件流水迁移到 6.2 统一 IoT 规则与事件台账。本文只负责设备侧；订单侧配置和押品流水迁移见 [订单侧历史数据迁移方案](../02订单侧规则与流水迁移/6.1→6.2 订单规则与押品流水迁移.md)。三旧模块（门禁事务记录、设备事务通知信息/配置）的业务兼容映射见 [6.1→6.2 门禁事务与设备事务通知兼容映射](../03业务兼容映射/6.1→6.2 门禁事务与设备事务通知兼容映射.md)。
>
> **上级索引**：[历史迁移总索引](../历史迁移总索引.md)
>
> **版本**：V3.0 | **编制日期**：2026-08-21 | **适用环境**：MySQL 8.0+ / TiDB
>
> **等级依赖**：[03/01 预警等级](../../03-预警配置/01预警等级/预警等级业务规则规格.md)；等级解析必须使用租户内 `severity_level_id`，不得在 SQL 中写死 `L1~L5`。

## 一、迁移目标

1. 合并老设备规则和事务通知规则到 `iot_rule_config`；保留合法的 05 附录 A 子类型，非法/未知子类型进入异常清单。
2. 设备规则和事件流水均保存 `severity_level_id`，并固化编码、名称、颜色、`sort_order` 快照；严重度只按 `sort_order` 比较。
3. 同一租户、设备、子类型的未处理历史事件可按原有 05 聚合规则合并，时间轴保留每一条原始触发；已处理流水不改变业务结果。
4. 迁移批次可重跑、可回滚；图片仅保留 OSS key；历史数据不触发新的 06 穿透通知。
5. `notify_channels` 迁移时须从 JSON 数组中剔除「站内信」；6.2 系统小角标在运行时自动更新，不可作为配置项持久化。

## 二、源类型与合法子类型

| 设备大类 | 迁移后的合法子类型示例 | 事件性质 |
| :--- | :--- | :--- |
| 图像识别预警 | 行人入侵、车辆入侵、形态变化 | 持续/瞬态按 05 附录 A |
| 设备物联预警 | 温度异常、湿度异常、气体异常、设备离线 | 持续 |
| 智能挂锁预警 | 拆壳、被剪、撬锁、非法开箱、正常开关锁事务、低电量、门锁离线 | 瞬态/持续 |
| 人脸门禁预警 | 人脸不匹配、门打开超时、正常刷脸通行 | 瞬态/持续 |
| GPS 预警 | 出围栏、超速、设备拆除、设备离线 | 持续/瞬态 |

旧系统中不在 05 权威枚举中的挂锁撬锁编码只能写入 `legacy_sub_type`，并进入 `migration_exception`，不得作为 6.2 可配置子类型或用例数据。

## 三、动态等级解析

每条老规则和每条历史事件分别执行以下优先级：

1. 老数据已有等级 ID，校验租户归属后使用；
2. 按同租户 `severity_code` 精确匹配；
3. 按同租户等级名称唯一匹配；
4. 使用迁移批次前经业务确认的 `tenant_legacy_severity_map`；
5. 仍无法匹配则写异常清单，保留原始等级展示快照，标记 `UNRESOLVED`，不伪造默认等级。

新规则/事件必须包含：

```text
severity_level_id
severity_code
severity_name
severity_color
sort_order_snapshot
sync_to_order_warn_snapshot
```

## 四、目标表关键结构

```sql
CREATE TABLE IF NOT EXISTS iot_rule_config (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  iot_rule_id VARCHAR(64) NOT NULL,
  tenant_id VARCHAR(64) NOT NULL,
  rule_name VARCHAR(50) NOT NULL,
  device_category VARCHAR(32) NOT NULL,
  sub_types JSON NOT NULL,
  device_ids JSON NULL,
  severity_level_id VARCHAR(64) NULL,
  severity_code VARCHAR(16) NULL,
  severity_name VARCHAR(32) NULL,
  severity_color VARCHAR(16) NULL,
  sort_order_snapshot INT NULL,
  sync_to_order_warn_snapshot TINYINT(1) NOT NULL DEFAULT 0,
  debounce_params JSON NULL,
  notify_channels JSON NULL,
  notify_user_ids JSON NULL,
  upgrade_days INT NOT NULL DEFAULT 0,
  upgrade_user_ids JSON NULL,
  status VARCHAR(16) NOT NULL DEFAULT 'ACTIVE',
  migration_batch_id VARCHAR(64) NULL,
  legacy_rule_ids JSON NULL,
  version INT NOT NULL DEFAULT 1,
  is_deleted TINYINT(1) NOT NULL DEFAULT 0,
  created_time DATETIME NOT NULL,
  updated_time DATETIME NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_iot_rule_id (iot_rule_id),
  KEY idx_tenant_status (tenant_id, status, is_deleted),
  KEY idx_migration_batch (migration_batch_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- iot_event_ledger 需增加下列迁移字段；其他原有事件字段沿用 05 字段清单
ALTER TABLE iot_event_ledger
  ADD COLUMN IF NOT EXISTS severity_level_id VARCHAR(64) NULL,
  ADD COLUMN IF NOT EXISTS severity_code VARCHAR(16) NULL,
  ADD COLUMN IF NOT EXISTS severity_name VARCHAR(32) NULL,
  ADD COLUMN IF NOT EXISTS severity_color VARCHAR(16) NULL,
  ADD COLUMN IF NOT EXISTS sort_order_snapshot INT NULL,
  ADD COLUMN IF NOT EXISTS sync_to_order_warn_snapshot TINYINT(1) NOT NULL DEFAULT 0,
  ADD COLUMN IF NOT EXISTS legacy_sub_type VARCHAR(64) NULL,
  ADD COLUMN IF NOT EXISTS severity_resolution_status VARCHAR(24) NOT NULL DEFAULT 'RESOLVED',
  ADD COLUMN IF NOT EXISTS migration_batch_id VARCHAR(64) NULL;
```

## 五、迁移步骤

### Step 0：建立批次和映射

```sql
INSERT INTO migration_batch (migration_batch_id, module, source_version, status, started_at)
VALUES ('MIG-IOT-20260821-001', 'IOT_WARNING', '6.1', 'RUNNING', NOW());

SELECT tenant_id, COUNT(*)
FROM tenant_severity_level
WHERE status = 'ENABLED' AND is_deleted = 0
GROUP BY tenant_id;
```

在批次开始前维护 `tenant_legacy_severity_map`；任一租户的旧等级映射不完整，批次标记 `BLOCKED`，不得按子类型静默推断等级。

### Step 1：规则合流

将 `t_dev_warn_cfg` 与 `t_dev_event_cfg` 规范化到 `stg_iot_rule`，按 `tenant_id + rule_name + device_category + sub_type` 去重；设备和子类型冲突、未知子类型、跨租户等级引用写 `migration_exception`。

```sql
INSERT INTO iot_rule_config (
  iot_rule_id, tenant_id, rule_name, device_category, sub_types, device_ids,
  severity_level_id, severity_code, severity_name, severity_color,
  sort_order_snapshot, sync_to_order_warn_snapshot, debounce_params,
  notify_channels, notify_user_ids, upgrade_days, upgrade_user_ids,
  status, migration_batch_id, legacy_rule_ids, version, created_time, updated_time
)
SELECT
  CONCAT('MIG-IOT-', :batch_id, '-', SHA2(CONCAT(tenant_id, ':', source_rule_key), 256)),
  tenant_id, MAX(rule_name), device_category, JSON_ARRAYAGG(sub_type),
  JSON_MERGE_PRESERVE(JSON_ARRAY(), JSON_ARRAYAGG(device_id)),
  MAX(severity_level_id), MAX(severity_code), MAX(severity_name), MAX(severity_color),
  MAX(sort_order), MAX(sync_to_order_warn), MAX(debounce_params),
  MAX(notify_channels), MAX(notify_user_ids), MAX(upgrade_days), MAX(upgrade_user_ids),
  'ACTIVE', :batch_id, JSON_ARRAYAGG(legacy_rule_id), 1,
  MIN(created_time), MAX(updated_time)
FROM stg_iot_rule
WHERE migration_status = 'READY'
GROUP BY tenant_id, source_rule_key, device_category;
```

事务通知规则按 05 附录 A 合流为同一 `iot_rule_config` 的子类型，不新建一个虚假的通知等级。历史正常通行事务仍按事件规则落账，但默认状态遵循 05 的瞬态自动处理规则。

### Step 2：事件流水迁移与聚合

- 已处理事件：按事件 ID 1:1 迁移，保留原处理人、时间和材料。
- 未处理持续型事件：按 `tenant_id + device_id + sub_type` 聚合为 1 条 `PENDING_VALID`，`trigger_count` 取原条数，首末时间取 MIN/MAX，所有明细写 `iot_event_timeline`。
- 瞬态事务：每条事件单独落账并置 `PROCESSED`，处理方式为 `SYSTEM`，不进入频次聚合。
- 事件等级、同步开关和规则快照取触发时解析结果；字典后续变化不回写。
- 历史迁移事件 `event_source=HISTORY_MIGRATION`，不触发 06 穿透通知；如需补发必须走单独重放任务并使用幂等事件 ID。

## 六、校验与验收

```sql
-- 规则数量和批次完整性
SELECT COUNT(*) FROM iot_rule_config WHERE migration_batch_id = :batch_id;
SELECT COUNT(*) FROM migration_exception WHERE migration_batch_id = :batch_id;

-- 等级必须同租户，且解析成功的记录不允许缺快照
SELECT e.event_id
FROM iot_event_ledger e
LEFT JOIN tenant_severity_level l ON l.severity_level_id = e.severity_level_id
WHERE e.migration_batch_id = :batch_id
  AND e.severity_resolution_status = 'RESOLVED'
  AND (l.severity_level_id IS NULL OR l.tenant_id <> e.tenant_id
       OR e.sort_order_snapshot IS NULL);

-- 未处理聚合后的唯一性
SELECT tenant_id, device_id, sub_type, COUNT(*)
FROM iot_event_ledger
WHERE migration_batch_id = :batch_id AND process_status = 'PENDING_VALID'
GROUP BY tenant_id, device_id, sub_type HAVING COUNT(*) > 1;
```

通过条件：未知子类型均有异常记录；已解析等级 ID 归属正确；持续型未处理事件无重复；时间轴条数等于原始触发条数；迁移不产生新穿透通知；图片可通过签名服务访问；抽样覆盖温度自动恢复、挂锁破坏人工解除、正常开锁事务、无权限仓库四类场景。

## 七、回滚

```sql
START TRANSACTION;
DELETE FROM iot_event_timeline WHERE migration_batch_id = :batch_id;
DELETE FROM iot_event_ledger WHERE migration_batch_id = :batch_id;
DELETE FROM iot_rule_config WHERE migration_batch_id = :batch_id;
DELETE FROM migration_exception WHERE migration_batch_id = :batch_id;
UPDATE migration_batch SET status = 'ROLLED_BACK', finished_at = NOW()
WHERE migration_batch_id = :batch_id;
COMMIT;
```

禁止 `TRUNCATE`、禁止按时间或状态删除、禁止删除上线后非本批次新增数据。重跑必须使用新批次号；回滚前停止该批次规则监听和补偿任务。
