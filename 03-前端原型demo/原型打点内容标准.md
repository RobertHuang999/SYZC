> **全局真源**：仓库根目录 [`AGENTS.md`](../AGENTS.md) **4.2 原型标注标杆标准**。
> **本文定位**：4.2 的**细则落地版**——把"打点要写全"翻译成**每一页必须交出的具体内容**，谁写、写在哪、写到什么程度，一目了然。
> **双端规则**：[`原型双端标注对齐说明.md`](./原型双端标注对齐说明.md)（一套正文、H5 只补端差异）。

## 1. 为什么要有这份标准

打点不是"页面上挂几个红点就算完"。研发看原型时，真正要回答的只有三个问题：

1. **这个字段是什么规格？**（控件、必填、长度、取值、新增和编辑有什么不一样、填错了提示什么）
2. **这个操作点下去会发生什么？**（谁能点、什么状态能点、校验什么、流转到哪、失败给什么提示）
3. **这条规则从哪来、和上下游什么关系？**（规则编号、真源文档在哪、和其他模块怎么联动）

**标杆页面**做到了这三件事，所以好用：

- 用户中心 → 合作方档案 → 货主信息：[`shared/partner-archives/annotations/`](./shared/partner-archives/annotations/)（每页 5～9 个点、2 张流转图、3～4 张字段字典表）
- 物联网 IoT 与预警 → 预警配置 → 设备预警配置：[`B端PC/src/features/device-warning-configs/annotations/`](./B端PC/src/features/device-warning-configs/annotations/)（每页 6～7 个点、页面级流转图、表单字段字典表）

**现状（2026-11-13 全量补齐后）**：全库 112 个打点内容文件（含 7 个模块的共享正文），**四类覆盖、流转图、字段字典表三项 100% 达标**；段落定位覆盖 105/112（94%），其余 7 个文件因文档动态生成或未挂载，不宜写死锚点。

> 打点文件的**迭代版本**以 `02-PRD文档/B-迭代需求/` 各版本目录为准；任何迭代目录里都没有的模块，一律记为「初始化版本」。体检报告按版本分组，可直接看每批欠账。注意：**客户融资 5 个菜单属 6.1，不在 6.3**（6.3 只改了同属融资监管的监管办理 / 监管管理）。

## 2. 四类打点，各自必须写什么

打点类型用 `kind` 字段区分（`页面` / `字段` / `交互` / `规则`），**每一类的内容下限不同**。

| 类型（kind） | 挂在哪 | **必须写到的内容** | 不合格的表现 |
| :--- | :--- | :--- | :--- |
| **页面** | 页面根、页头单号/标题区 | ①一句话说清这页干什么；②**业务生命周期流转图**（Mermaid）；③上下游数据从哪来、流向哪、快照何时固化；④谁能看/谁能改（角色 + 数据范围） | 只写"这是预警列表页"之类定位句，没有流转图 |
| **字段** | 字段区块、表单卡片、详情子板块、列表表格 | **字段字典表**（见第 3 节模板），字段名一律用**中文业务名**，不写 `warehouse_name` 这类研发字段名 | 用一段话描述"名称必填、编号唯一" |
| **交互** | 页头按钮区、行操作列、弹窗、抽屉 | ①**操作矩阵**（见第 3 节模板）：哪个角色、哪种状态、看得到哪个按钮；②点下去做什么（校验/流转/调接口）；③二次确认与必填理由；④成功提示、失败提示的**原话** | 只写"点击保存后生效" |
| **规则** | 受规则约束的控件 | ①规则全称+编号（如 `【设备范围唯一性规则】(R04)`）；②触发条件；③拦截后给用户看的那句话；④真源在三件套哪一节 | 只丢一个编号 `R04`，不写名称也不写条件 |

> **规则引用一律写全名**（`【规则名称】(编号)`），禁止单抛 `R04`、`P01`——与 `AGENTS.md` 4.0.7 一致。

## 3. 三个必用模板（直接复制，别自己发挥）

### 3.1 字段字典表（6 列，字段类打点专用）

```markdown
| 字段名称 | 控件类型 | 必填 | 取值范围与格式 | 新增/编辑差异 | 校验与提示 |
| :--- | :--- | :---: | :--- | :--- | :--- |
| **规则名称** | 单行文本 | 必填 | 最多 50 个字符，租户内唯一 | 新增可填，编辑只读 | 失焦与提交双重校验；重复时提示「该规则名称已存在，请换一个」 |
| **预警等级** | 下拉单选 | 必填 | 仅可选本租户已启用的等级（2～20 档） | 新增、编辑均可改 | 无可选等级时提示「请先到预警等级配置里启用等级」 |
```

- **只写列表/表格可见的字段**时，把「新增/编辑差异」一列换成「列表展示规则」（是否省略、超长怎么处理）。
- 字段多时**按区块拆成多张表**，一张表别超过 12 行，否则评审时看不清。

### 3.2 操作矩阵（6 列，交互类打点专用）

```markdown
| 操作 | 可见角色 | 可见状态 | 点击后发生什么 | 二次确认 / 必填 | 成功提示 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **停用** | 风控专员 | 生效中 | 规则转为停用，暂停匹配新回调；未处理预警流水不受影响 | 弹窗确认，理由选填（最多 200 字） | 「已停用，正在匹配的预警不受影响」 |
```

### 3.3 页面流转图（Mermaid，页面类打点专用）

```ts
{
  label: "生命周期流转图",
  content: `flowchart TD
    A["新增录入"] -->|"保存生效"| B["生效中"]
    B -->|"人工停用"| C["停用"]
    C -->|"重新启用"| B
    B -->|"解绑全部设备"| D["已失效（不可逆、禁编辑）"]`,
}
```

- 优先用 `flowchart TD`（竖向）或 `flowchart LR`（横向）；状态机复杂时用 `stateDiagram-v2`。
- **必须画在"页面"类打点里**；字段/交互类打点不再重复画同一张图。

## 4. 每个页面最少写几个点

按下表执行，**"页面"类为强制项**，其余按页面类型取最低条数。

| 页面类型 | 页面级（页面） | 字段级（字段） | 交互级（交互） | 规则级（规则） | 合计最低 |
| :--- | :---: | :---: | :---: | :---: | :---: |
| **列表页** | 1（含流转图） | ≥1（列表列字段字典） | ≥1（行操作 + 筛选） | 涉及规则的取数/状态至少 1 | **4** |
| **详情页** | 1（含流转图） | ≥2（各主要子板块） | ≥1（页头操作矩阵） | 按需 ≥1 | **4** |
| **新增/编辑/配置页** | 1（含流转图） | ≥1（字段字典表） | ≥1（保存/提交与 Dirty 拦截） | 按需 ≥1 | **4** |
| **弹窗 / 抽屉** | 可不挂 | ≥1 | ≥1（确认/取消/必填理由） | 按需 | **2** |

**硬性判定口径**（给评审和脚本用）：

- 一页至少要有 **1 个 `kind: "页面"`**，且该页所有打点里**至少 1 张 Mermaid 图**。
- 有表单或详情字段区的页面，**至少 1 个 `kind: "字段"`**，且**至少 1 张字段字典表**。
- 有按钮、行操作、弹窗的页面，**至少 1 个 `kind: "交互"`**。
- 只挂文档、不写打点的页面，视为**未交付标注**。

## 5. 段落定位（documentRefs）：从红点直接跳到 PRD 原文

打点卡片顶部有【查字段】【读PRD】【看规则】三个按钮。要让它们**跳到对应章节而不是文档开头**，每条打点都要配 `documentRefs`：

```ts
documentRefs: {
  fields: { section: "一、基础识别与列表业务字段", match: "预警状态", element: "row" },
  prd:    { section: "4.4 H5 移动端", match: "列表形态", element: "text" },
  rules:  { section: "一、能力定位", match: "逐条独立落账", element: "text" },
}
```

- `section` 写三件套里的**章节标题原文**；`match` 写该章节里**独一无二的一小段原文**；`element` 按跳转目标取 `row`（表格行）或 `text`（正文）。
- **新页面强制配齐**；存量已批量补齐，现状 98/105 个文件、809 条锚点（其中 808 条经脚本校验能在文档里找到，剩 1 条因动态文档集合无法静态验证）。
- **别手写锚点**：用 `npm run gen:doc-refs` 自动生成，用 `npm run check:doc-refs` 校验；手写的 section / match 很容易和文档标题对不上（这正是之前 100 多条失效锚点的原因）。
- 改三件套章节标题后，**必须跑一遍 `npm run check:doc-refs`**，失效的会被列出来，可加 `--drop` 删掉后重新生成。

## 7. 命名与编号（照抄即可）

| 项目 | 规则 | 例子 |
| :--- | :--- | :--- |
| `id` | `{模块}-{页面}-{语义}`，全小写连字符，页面内唯一 | `partner-archive-detail-account` |
| `number` | 页面内从 1 连续不跳号；**顺序 = 页面从上到下、从左到右的阅读顺序** | 1 页面 → 2 页头操作 → 3 字段区 … |
| `targetId` | 与页面 `PrototypeAnnotationTarget` 的 `annotationIds` 一致 | 同上 |
| `title` | 一句话说清这块是什么，**不超过 30 字** | "关联客户账号 · C端 1:1 绑定关系" |
| `content` | 卡片首屏摘要 1～2 句大白话，**不放规则编号长清单** | "以 18 位身份证号为租户内唯一主键…" |
| `details` | 深度材料放这里，按「字段字典 / 操作矩阵 / 流转图 / 约束」分组 | — |

## 8. 体检脚本：一条命令看出哪页没写全

```bash
npm run check:annotations
```

脚本会扫描 `shared/` 与 `B端PC`、`B端H5` 的 `annotations` 目录，逐文件统计：打点总数、四类覆盖、有没有 Mermaid、有没有字段字典表、`documentRefs` 覆盖、纯转发文件是否指到了共享正文；然后输出：

- 终端摘要（总数、达标页数、问题条数）
- 明细报告 `03-前端原型demo/tools/标注体检报告.md`（按模块列出缺口，可直接当整改清单）

**段落定位另有两个命令**：

```bash
npm run check:doc-refs   # 校验每条锚点的 section / match 能否在挂载文档里找到
npm run gen:doc-refs     # 给还没配锚点的打点自动生成（按标题与正文相似度选章节）
```

- `check:doc-refs` 加 `--verbose` 看具体失效项，加 `--drop` 删掉失效块（删完再跑 `gen:doc-refs` 重生成）。
- `gen:doc-refs` 选章节、选文本都按相似度打分，宁可不加也不写假锚点。

脚本是**报告模式**：发现问题只提示、不阻断构建。等存量补齐、规则稳定后，再视情况切到 `--strict` 阻断。

**双端判定口径**：脚本只在 PC 与 H5 **挂载同一份三件套**时，才把"H5 自写正文"记为不达标。若 H5 模块有自己独立的三件套（例如 H5 入库管理 vs PC 入库记录，业务规则规格里明确互相引用），则不强制合并，只统计内容深度。

## 11. 常见走样（对照自查）

| 走样写法 | 问题 | 改成 |
| :--- | :--- | :--- |
| "名称必填，编号唯一" | 研发不知道控件、长度、提示语 | 字段字典表一行说全 |
| "点击保存后生效" | 不知道校验什么、失败说什么 | 操作矩阵 + 流转图 |
| 一页只有 2 个点 | 覆盖不到字段和交互 | 按第 4 节下限补齐 |
| 把 PRD 整段粘进 `content` | 卡片首屏看不动 | 摘要留在 `content`，正文放 `details` 或三件套 |
| `R04` 单独出现 | 研发要回查编号表 | `【设备范围唯一性规则】(R04)` |
| H5 另写一套规则结论 | 双端说法打架 | 回到 shared 正文，H5 只补差异句 |
